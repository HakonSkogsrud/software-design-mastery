# Lecture Notes - Ports & Adapters

## Overview

In this lesson, you learned how to keep your application's business logic independent from frameworks, databases, and other infrastructure concerns using the **Ports & Adapters** architectural style (also known as **Hexagonal Architecture**).

The central idea is that your application's core should define what it needs, while external systems adapt to those requirements. This leads to better dependency direction, improved testability, and software that is easier to evolve over time.

By the end of this lesson, you should understand:

- Why APIs should not become the center of your application
- What Ports and Adapters are
- How to separate HTTP concerns from business logic
- How Protocols naturally serve as ports in Python
- Why dependency direction is more important than dependency injection
- How this architecture enables multiple delivery mechanisms
- Common mistakes to avoid

---

# When the API Becomes the Application

As the finance platform grows, it begins exposing functionality through a REST API.

Typical endpoints might include:

- `POST /transactions`
- `GET /summary`

At first, these endpoints are small. Over time, however, they often accumulate responsibilities such as:

- validating requests
- creating domain objects
- executing business rules
- storing data
- generating reports
- formatting responses

Eventually, the API layer contains most of the application's behavior.

This creates a tightly coupled system where the framework effectively dictates the application's architecture.

Ask yourself:

- What happens if you replace FastAPI?
- What if you later need a CLI?
- What if reports should also be generated by scheduled jobs?
- What if messages arrive through a queue instead of HTTP?

If all application logic lives inside API endpoints, adapting to these changes becomes much more difficult.

---

# Problems with the Naive Approach

In the initial implementation, the endpoints:

- create domain objects
- manipulate storage
- execute workflows
- generate reports
- return HTTP responses

This mixes multiple concerns into a single place.

Some consequences include:

- Business logic becomes dependent on HTTP.
- Storage becomes tightly coupled to the API.
- Framework-specific code spreads throughout the application.
- Testing requires the web framework instead of simple unit tests.

This weakens several CARDS principles:

- **Alignment** — dependencies point toward the framework instead of the domain.
- **Separation** — HTTP and business logic become intertwined.
- **Resilience** — infrastructure changes affect core application logic.

---

# The Core Idea of Ports & Adapters

Infrastructure changes frequently.

Business rules usually do not.

Frameworks evolve.

Databases change.

Deployment mechanisms change.

The application's core logic is generally much more stable.

Instead of allowing infrastructure to define your application, reverse the dependency direction.

The application should define what it needs.

Infrastructure should satisfy those needs.

This is the central idea behind Ports & Adapters.

---

# Ports

A **port** describes a capability the application depends on.

For example, the finance platform needs a way to store and retrieve transactions.

Rather than depending directly on PostgreSQL or SQLite, the application defines an interface that expresses this capability.

In Python, Protocols are an excellent fit for ports because they define behavior without requiring inheritance.

A repository port might simply describe operations such as:

- add a transaction
- retrieve all transactions

Notice that these methods describe **application concepts**, not database operations.

The application owns the interface.

Infrastructure implements it.

---

# Application Use Cases

The next step is moving business workflows out of the API layer.

Instead of endpoints containing application logic, create framework-independent use cases such as:

- creating transactions
- generating monthly reports

These functions depend only on:

- domain objects
- ports

They know nothing about:

- FastAPI
- HTTP requests
- JSON
- SQL
- databases

This is the major architectural shift in the lesson.

Your business logic becomes reusable regardless of how it is invoked.

---

# Adapters

Adapters provide concrete implementations of the application's ports.

For example:

- an in-memory repository
- a SQLite repository
- a PostgreSQL repository
- a repository backed by an external finance API

All satisfy the same interface expected by the application.

Because the application only depends on the port, infrastructure can change without affecting business logic.

Infrastructure remains at the edges of the system.

---

# The REST API Becomes an Adapter

After introducing use cases and ports, the REST API becomes much simpler.

Its responsibilities are now limited to:

- parsing HTTP requests
- converting incoming data into domain objects
- calling application use cases
- formatting HTTP responses

It no longer contains business workflows.

This is the key insight of the lesson:

> **The API is not the application.**

It is simply another adapter around the application core.

---

# Better Testability

One of the immediate benefits of this architecture is testing.

Without Ports & Adapters:

- tests often require HTTP requests
- framework setup becomes necessary
- storage concerns leak into tests

With Ports & Adapters:

- use cases can be tested directly
- fake repositories are easy to create
- no framework is required
- tests become fast and focused

Because the application depends on a port rather than a concrete implementation, substituting a fake implementation becomes straightforward.

---

# Multiple Delivery Mechanisms

Once the application logic is independent from the API, it becomes reusable in many different contexts.

The exact same use cases could now be invoked from:

- a REST API
- a command-line interface
- scheduled jobs
- batch imports
- background workers
- asynchronous message consumers

Each of these is simply another adapter.

The application core remains unchanged.

---

# Dependency Direction

One of the most important architectural ideas introduced in this lesson is dependency direction.

Rather than having the application depend directly on frameworks and databases, dependencies should point inward toward the application core.

Conceptually:

```text
REST API Adapter
       │
       ▼
Application Core
       │
       ▼
Repository Port
       ▲
       │
Database Adapter
```

Notice that:

- adapters depend on the application
- the application does **not** depend on adapters

This keeps the core stable while infrastructure evolves around it.

---

# AI Guardrail

AI coding assistants often generate code that places entire workflows inside API endpoints because that is the most direct solution.

Although the generated code may work correctly, it frequently produces tightly coupled designs where:

- endpoints contain business logic
- database calls
- notifications
- reporting
- orchestration

Good architecture provides boundaries that AI-generated code naturally fits into.

Instead of asking AI to generate complete endpoints, ask it to implement:

- use cases
- repository adapters
- API adapters

within an existing architecture.

The architecture becomes a safety rail that keeps AI-generated code maintainable.

---

# Common Mistakes

## Putting business logic back into endpoints

Endpoints should only:

- parse requests
- call use cases
- format responses

They should not implement workflows.

---

## Designing ports around infrastructure

Avoid interfaces such as:

- `save_to_postgres()`

Instead, ports should describe application capabilities, for example:

- add transaction
- list transactions

The application should not know—or care—how those capabilities are implemented.

---

## Overengineering small applications

Not every project needs multiple architectural layers.

Ports and adapters become valuable when infrastructure begins changing independently from business logic.

Architectural boundaries should emerge because of real pressure, not because every project "should" use a particular pattern.

---

## Letting frameworks dictate architecture

Frameworks provide delivery mechanisms.

They should not determine:

- where business logic lives
- dependency direction
- the structure of the domain model

The application should own those decisions.

# CARDS Connections

This lesson reinforces several parts of the CARDS framework.

## Alignment

Dependencies point toward the application core instead of external infrastructure.

---

## Separation

Business logic is isolated from HTTP, databases, and frameworks.

---

## Resilience

Infrastructure can evolve independently from the application core, reducing the impact of future changes.

---

# Key Takeaways

- APIs, databases, and frameworks are delivery mechanisms.
- Business logic belongs in the application core.
- Ports define what the application needs.
- Adapters implement those requirements.
- Protocols provide lightweight ports in Python.
- Better dependency direction improves testing and long-term maintainability.
- Stable business logic should be protected from changing infrastructure.

The most important mental model to remember is:

> **The API is not the application.**
>
> **The database is not the application.**
>
> **They are adapters around the application.**
